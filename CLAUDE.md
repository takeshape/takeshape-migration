# TakeShape migration

TakeShape shuts down on **December 31, 2026**; every project is deleted that day with its content and assets, and its APIs stop answering. This repo holds the guides and scripts for moving customers off TakeShape. It is public. The private archive is `takeshape/takeshape-migration-archive`. Write nothing here that names a customer or points back to one: put "a large customer site" where a name, a domain, shape or page names, or counts from a customer's site would go. Leave out Cloudflare account addresses, deploy version IDs and paths from TakeShape's private source too.

Owner: Mark Catalano, TakeShape co-founder. The EmDash work started in a Claude session on 2026-10-05 and moved here on 2026-10-14.

## Node and TypeScript

- Minimum Node is 22.18 for the repo and for customers: the first 22.x that runs TypeScript without a flag. Node 22.17 fails with `Unknown file extension ".mts"`. `.nvmrc` pins 26 for day-to-day work. CI runs the suite on 22.18.0 and 26. Three more CI jobs run on 26 only: `test:tsg-templates`, `test:tsg-e2e -- shape-books` (Node mode) and `test:tsg-e2e -- shape-books --cloudflare` (Node mode again, then the site transfer into local D1 and R2 under `astro dev` on workerd and the Workers build under `astro preview`, with no Cloudflare account). The Cloudflare job was added on 2026-10-17, after a regression in `astro dev` on the Cloudflare config (since fixed) went unnoticed because only Node mode ran. They keep npm's download cache but not `test/.cache/`, so the e2e's generated project, which has no lockfile, gets a fresh `npm install` each run, as a customer's would. A failed e2e uploads its `test/.out/tsg-e2e-shape-books*` files as an artifact (`tsg-e2e-shape-books` or `tsg-e2e-shape-books-cloudflare`).
- npm is not set to `engine-strict`. Two of emdash's own dependencies (1.1.0 through 1.3.1 alike) ask for more than emdash does (`undici` >=22.19, `@emdash-cms/registry-verification` ^22.22.2), so a strict install would refuse 22.18 even though everything runs there. Installs on 22.18 print two `EBADENGINE` warnings.
- Node only strips types, it never compiles. Use erasable syntax only (`erasableSyntaxOnly` enforces it): no `enum`, `namespace` or constructor parameter properties, and type-only imports use `import type`. Imports of real packages stay dynamic (`load()`), so a missing helper gets a readable error.
- The `.mts` extension forces ES modules, so the script runs the same in a customer project whatever its `package.json` says.
- Generated projects need Node 22.22 or later, Astro 7.4's minimum, and their `package.json` says so. So do `test:tsg-templates` and `test:tsg-e2e`, which build them. Everything else in the repo keeps 22.18.
- Seed output is typed with emdash's own `SeedFile`, `SeedCollection`, `SeedField` and friends. Seeds from the TypeScript version matched the JavaScript version on all nine fixtures, apart from the random `_key` values EmDash's HTML converter assigned on every run. Since the converter writes Portable Text from Draft.js itself (2026-10-15), keys come from Draft.js and two runs give identical seeds.

## How the converter works

1. Finds `schema.json` and `data.jsonl` (unzips first if given a `.zip`).
2. Plans each stored shape: `multiple` shapes become routable collections (plural snake_case), `single` shapes become one-entry non-routable collections, `taxonomy` shapes with only a label (and maybe a slug) become EmDash taxonomies. Taxonomy shapes with extra fields stay collections so nothing is lost. Every collection, single ones included, gets four legacy fields: `takeshape_id`, `takeshape_published_at` (`_enabledAt`), `takeshape_created_at` and `takeshape_updated_at`. `--no-legacy-fields` leaves out all four.
3. Plans each property from its JSON schema plus its form widget (`forms.<Shape>.default.properties.<prop>.widget`). The mapping table is in the guide under "How TakeShape maps to EmDash".
4. Converts values. Rich text: Draft.js converts straight to Portable Text, block for block, following TakeShape's renderer (draft-js 0.9.1 `convertFromRaw` and `stateToHTML`), with Draft.js block keys as `_key`s. Pullquotes, section breaks, empty paragraphs, underline, sub and sup, link targets and attributes, image alignment, size, caption, credit and link, and oEmbed HTML (as an `htmlBlock`) survive. What Portable Text can't hold goes into a per-entry json field, `takeshape_rich_text`, keyed by block `_key`, which the migrated site's renderer reads. Inline images inside paragraphs keep only their text, and atomic blocks with no template keep TakeShape's fallback HTML; the report counts both. Markdown and Block Canvas MDX go through EmDash's `markdownToPortableText`. Images and files become `$media` references that `emdash seed` downloads from assets.takeshape.io. Relationships become `$ref:` links. Taxonomy values also fill `takeshape_term_order`, each taxonomy's term slugs in TakeShape's order, because EmDash returns an entry's terms by label.
5. Pairs fields that point at each other (Post.author with Author.authored) into one EmDash relation when both store exactly the same links, and declares the links from the parent end only. One relation answers both ends with every link, so fields with different links stay separate: on a large customer site, two such fields, one of them inside an inline object, held different links (all but a few picks pointed back), and pairing them dropped hundreds of links and failed the seed (fixed 2026-10-16, `test/relations.test.mts`). shape-blog's `Post.author` and `Author.authored`, with every link on the post side, stay separate too.
6. Orders collections and entries so every `$ref:` target is created first. `emdash seed` creates collections one at a time and resolves `$ref:` only to entries it already created, so in collections that point at each other, a field whose links go to a collection created later becomes the child end of a relation, and a new field on the target collection (`<collection>_<field>`, left out of the field map) declares those links. Its label names the field it stands for. EmDash keeps `sort_order` on the parent end only, so a multiple field read from that end comes back in the declaring entries' order; the converter keeps each such field's TakeShape order in `takeshape_link_order` (the targets' TakeShape ids, per field, for entries with two links or more; named `linkOrder` in the field map), and the migrated site's loaders sort by it, links made in EmDash since coming last. A link from an entry to itself gets a stub the same way as a loop. Entries that link to each other in a loop inside one collection get a placeholder ("stub") entry first, with the same slug and id `<seedId>~stub`; the full entry later updates it. That is why every apply must use `--on-conflict update`.
7. With `--preload-media local` (design: `docs/superpowers/specs/2026-10-14-media-preload-design.md`), downloads every `$media` source once, 8 at a time, into `--uploads-dir` under keys it chooses (`ts-<asset id><ext>`, `ts-url-<hash><ext>`), and records each in a ledger (`takeshape-media.db`: EmDash's own tables plus `takeshape_media_sources`). A download counts only if its size matches `Content-Length`, and a source counts as done once its rows exist and its file is in storage at that size, so reruns and a clean redo (delete only `data.db`) download nothing. It upserts the media rows this seed uses into `--database`, rewrites each `$media` as the stored value, and leaves out what still fails after 3 attempts (listed in the report). Without the flag, the seed keeps `$media` and the report suggests the flag above 1,000 sources.
8. Writes the seed, `takeshape-field-map.json` next to it (`--field-map` moves it: per shape its collection or taxonomy, per property path the field slug and kind and any relation, the renamed slugs, the legacy field names; its `single` and `reverse` entries are for reading only, since tsg2astro takes both from the export's schema), and a report listing the field map, renamed slugs, dropped links, the drafts that published entries link to, rich text kept as text or as TakeShape's fallback HTML, styles with no EmDash mark, and rich-text and image links that still point at TakeShape's CDN.
9. With `--site <dir|tsg.yml>`, loads the site's `tsg.yml` as takeshape-ssg does (through `tsg2astro/site-slugs.mts`) and gives each routed entry the slug its old URL used (`slugg` of the path variable's value), so its page keeps its URL. Other entries step around those slugs. The report lists the entries whose slug differs from the run without `--site`, and any entry whose old URL can't be kept.

Overrides file format:

```json
{
  "shapes": { "Post": { "collection": "articles" }, "Draft": { "skip": true }, "Category": { "as": "collection" } },
  "fields": { "Post.legacyBody": { "skip": true }, "Post.deck": { "slug": "excerpt" } }
}
```

## How tsg2astro works

1. Reads `tsg.yml` as takeshape-ssg 12.21.1 does (defaults, lodash merge, `${env.X}` and `${key}` interpolation with `process.env`), the export and the field map.
2. Plans each route part (a plain page, item pages, listing pages, `firstPage`) by takeshape-ssg's rules. Page files follow the URL: `/blog/:title/` is `src/pages/blog/[title].astro`. Routes whose URLs overlap share one file that tries each in `tsg.yml` order, as the first route won in takeshape-ssg. A path with an extension becomes an endpoint with the old Content-Type, except a path ending in `index.html`, which is its folder's page (`/help/index.html` is `src/pages/help/index.astro`, served at `/help/`; `src/middleware.ts` sends `/help/index.html` there), as takeshape-ssg wrote the same file for both and its host served it at both URLs. `.` and `..` in a path resolve as in a URL, so page files stay under `src/pages/`. A URL takeshape-ssg never wrote gets a real 404, and a folder URL without its slash gets a 301 only when its page exists. A route whose page file is Astro's 404 route (`/404`) replaces the scaffold's generic `src/pages/404.astro`, and the report says it now answers unknown URLs and answers `/404` with status 404 (Astro forces that status, read from source); a route at `/404.html` gets a note on serving it for unknown URLs.
3. Parses every template the routes reach with Nunjucks 3.2.0's parser, and writes an Astro component per HTML template (markup line for line; `extends` and `block` as layouts with named slots; includes and macros as components; Nunjucks expression rules through `runtime/nunjucks.ts`) and a render function per text template. A name set in the branches of one if/elif/else chain becomes one value, a condition per branch, as Nunjucks 3.2.0 runs it: a branch without a set, or a chain without an else, keeps the name's old value, which is the context's (`Astro.props`, a text template's `ctx`). A name set again further down in the same frame gets a name per set, and each read and include the one set last before it (`versions.mts`); a child template's blocks read the last. Nunjucks's loop idioms translate too: a counter stepped at the end of a loop body, a list built with `concat`, and a chain in a loop that keeps the previous run's value where no branch sets it. Sets whose value still depends on run order stay in the report: sets in loops that write an outer name some other way, or a chain whose value reads what the loop body sets. Anything it can't write exactly goes in the report, never silently. Template and query names resolve from `templatePath` as takeshape-ssg's `path.join` did (`templateKey` in `scope.mts`, also written back into the parse tree). A name that leaves the templates folder but stays in the site folder (an SVG included from `static/`) is written under `src/templates/_site/` (or `src/loaders/_site/`) by its path from the site root; a name outside the site folder is reported as not translated and never read. An `image` filter parameter, or a literal value, that the image endpoint ignores (`imageParamProblem` in `runtime/imgix.ts`), parameters held in a variable, the same for rich-text `imageConfig` and `images` in queries, and for `imageDefaults` in `tsg.yml` each get an `image-param` item. A value the template computes isn't reported: it reaches the endpoint as it reached imgix (a large customer site passed `fit:crop` in many calls, with `crop` unquoted and never defined, so neither imgix nor the endpoint got a `fit`).
4. Plans each GraphQL query against the export's schema and the field map, and writes a loader that reads EmDash and returns the shape TakeShape's API answered with, so templates keep `item.title`. List status follows TakeShape's rules (see "TakeShape API behavior"). Each read names the columns its entries are built from (`select`, from `entryColumns()` in `emit-loader.mts`), and `runtime/rows.ts` reads only those, so a list printed for its titles reads no rich text. A list cut by `size` or `from` reads the columns that decide it for every entry, then the kept entries' columns. Item and listing pages pass the loader a pick (`itemPick` and `listingPick` in `runtime/context.ts`) that finds the page in the light list, so only its own items, and an item page's neighbors, are read in full and built; a route whose path reads anything but a plain value of the item (`pathValues()` in `emit-loader.mts`) builds the whole list. Reference and reverse fields are read for a whole list at once through `runtime/references.ts`, and reads that need nothing read before them go out together, one `Promise.all` per depth (see "Page speed on Workers"). `*Html` fields render through `runtime/richtext.ts` from the Portable Text and the `takeshape_rich_text` sidecar. `_id`, `_createdAt`, `_updatedAt` and `_enabledAt`, and sorts on them, read the `takeshape_*` fields through `fieldValue()` in `runtime/query.ts`, which falls back to EmDash's own id and dates (ISO strings) when a field is empty, so an entry made in EmDash after the move lists where TakeShape would have put it.
5. Copies the scaffold, the runtime (as `src/lib/takeshape/`) and `static/` (as `public/`), and writes `src/lib/takeshape/site.ts` (the `tsg.yml` settings the helpers need: routes, dates, locale, image defaults), `.env` (`EMDASH_SITE_URL` from `--site-url`) and the report. It scans static files and the site's `package.json` scripts for `takeshape.io` hosts.
6. Writes into an empty folder or one it wrote before, never inside the site folder (`--out` defaults to `emdash-site` in the working folder). The marker `.tsg2astro.json` lists the paths it owns, and a rerun deletes and rewrites only those, never `data.db`, `uploads/`, `.wrangler/`, `takeshape/`, `node_modules/` or `dist*`. Before writing, `checkOutputs()` in `scaffold.mts` normalizes every path, keeps it inside `--out` and in a path tsg2astro owns, and throws when two files share a path, naming what each was for. The same input gives the same output.

## TakeShape export format (as observed)

Two forms so far: the 2020 pattern exports in `test/fixtures/`, and the export TakeShape writes today (`test/tsg/sites/shape-books/export/`, 2026-10-16, schema 3.67.0). The converter and tsg2astro's schema reader take both.

- `data.jsonl`: one entry per line. `_id`, a shape id in `_shapeId` (newer exports) or `_contentTypeId` (older), `_enabled` (published), `_status` (workflow step id), `_enabledAt`, `_createdAt`, `_updatedAt`. Current exports add `_projectId`, `_namespace` (`{{PROJECT_ID}}.dev.<shape id>`) and `_contentTypeName`.
- Field values are keyed by **storage key**, the suffix of the property's `@mapping` (`takeshape:local:Post.rybsZhDU-` in 2020, `shapedb:Post.rJgad7TLZ` now), not by property name. Inline objects nest the same way.
- Relationships: before schema 3.18, the property has `@relationship: {shapeIds, type, relatedName}`. Current exports have `@resolver: {name: "shapedb:getRelated"}` with `@ref: "local:Author"` (`items.@ref` for a list) and the reverse name in `@backreference.name`. ts2emdash's `legacyRelationships()` rewrites the new form into the old when the schema loads, and `relationshipOf()` in `tsg2astro/schema.mts` reads both. TakeShape's own source converts between the two forms too.
- Relationship values are `{ "shapeId" | "contentTypeId": "<shape id>", "id": "<entry id>" }`. Current exports add `"_shapeId": "TSRelationship"`.
- Assets are rows with shape id `ASSET`. `path` lives under storage key `Hk6FQuz5`. Current exports write it as `{{PROJECT_ID}}/dev/<asset id>/<file>`, keep the project's id in each row's `_projectId`, and strip `schema.projectId`. The converter fills the placeholder from `_projectId`, then `schema.projectId`, and the report warns when neither exists. Current asset rows also hold `SJXSidnXE`, an images.takeshape.io URL.
- `apiVersion` is "2" in every fixture and "1" in the shape-books export, which has `workflows: {}` (see the next section).
- Draft.js is stored as a JSON string. Entity types seen: `LINK`, `image` (`data.id` is an asset id; caption and credit are nested Draft.js), `oembed` (`data.html` holds an iframe).
- Shapes without `model` are inline objects or service shapes; properties with `@resolver` and no `@mapping` come from connected services and are not stored.

## TakeShape API behavior (TakeShape's API source, read 2026-10-15)

The site translator's loaders follow these rules.

- A list query (`getXList`, and reverse fields like `Author.authored`) returns published entries only when it has neither `where` nor `filter`. Its `onlyEnabled` argument defaults to `true`, and the API applies it only when no `where` and no `filter` is passed, as `_status` in the workflow's live steps, falling back to `_enabled` for entries without `_status`. The `default` workflow those steps come from is added to the runtime schema for `apiVersion` 2 and up; every fixture is `apiVersion` "2". Any `where` or `filter` drops the default, so unpublished entries come back unless that clause filters on `_enabled` itself. The API key plays no part.
- Without a workflow, `onlyEnabled` filters nothing, not even on `_enabled`. The API collects the live steps of the shape's workflow (its own, else `default`) and adds no condition when it finds none, so the list keeps only its own fixed conditions. The `_enabled` fallback lives inside the `_status` condition. `default` is added only from `apiVersion` 2.0.0, so in an `apiVersion` "1" project with `workflows: {}`, like the 2026 shape-books export, every list returns unpublished entries too. `tsg2astro/list-status.mts` follows this per shape.
- A list query without `size` returns at most 20 entries, and `total` still counts every match. The default order is `_createdAt` descending, and every sort gets `_score` as its last key. `size` above 250 is an error.
- Relationship fields return their targets whatever their status, in stored order; a multiple relationship drops missing targets.
- Reverse fields are the same list query with a fixed condition on the referring property. Without a `relatedName` the field is `<camelCase shape name>Set`, and schemas older than 3.13 get one for every relationship.

## TakeShape's CDN (checked 2026-10-14)

- `https://assets.takeshape.io/<path>` is S3 behind CloudFront and serves the original bytes of every asset, images included. The converter uses it for all `$media` URLs and for `--download-assets`.
- `https://images.takeshape.io/<path>` is imgix and recompresses. Customer sites mostly used this host, so rich-text links to it still show up in the report. Checked 2026-10-16 with shape-books images: it treats every URL as `auto=compress,format`. `w=300` alone gave the same bytes as `w=300&auto=compress,format` and as `w=300&q=45` (6,847 or 6,848), against 10,559 at `q=75`; an empty `auto=` gave 13,230. It sends AVIF or WebP when the `Accept` header lists them and JPEG otherwise (`image/png`, `*/*` or none), even for `fm=png`. On 2026-10-14, PNGs with real transparency stayed PNG for an `Accept` without WebP or AVIF.
- imgix's `fit=fill` and `fit=fillmax` pad only when told how: `fill=solid`, a `fill-color` or a `bg`. Without one, an 800x498 PNG at `w=1000&h=1000&fit=fill` came back 1000x623, and the 412x600 PNG at `w=600&h=600&fit=fillmax` came back 412x600 (2026-10-16).
- Both hosts accept a `'` in the path raw or as `%27`.
- A compare against a live site used to fetch every old image from imgix. A large customer site's golden pages held over ten thousand imgix URLs in about two dozen distinct parameter sets (2026-10-20). A setting also counts the source's type, its orientation and whether it is smaller than the box, so there are more settings than parameter sets. A compare of a few hundred of that site's pages with `--media` (2026-10-20, Node build, `--max-pages`) asked imgix only for its samples, a few dozen, and assets.takeshape.io only for the handful of originals the ledger lacked, each once (some of them TakeShape no longer had). The old compare fetched each of those pages' thousands of distinct TakeShape image URLs one by one. Site moves therefore always run the converter with `--preload-media local`.
- Node 26's fetch talks HTTP/2 to `assets.takeshape.io` (Node 22.18 gets HTTP/1.1), and a stream can end early without an error: on 2026-10-15 a preload stored `acme-1.png` at 15,961 of 25,827 bytes. The converter now checks every download against `Content-Length`, in the preload and in `--download-assets`. `emdash seed`'s own `$media` downloads have no such check, which is EmDash code, so when a live comparison fails, check which side matches `curl` first.

EmDash's caching, read from source, not turned on:

- Astro's route cache would serve repeat views without running the Worker. It takes `cache: { provider: cacheCloudflare() }` (`@astrojs/cloudflare/cache`, Workers cache with `Cache-Tag` purge) in `astro.config.mjs`, and each page calling `Astro.cache.set({ tags, maxAge })` with a tag for every collection and taxonomy it read. Loaders drop EmDash's cache hints today, so `emdash-api.ts` would have to collect the tags. EmDash purges `[collection, entry id]` on every content write through its API (update, publish, unpublish, schedule, restore, delete), `emdash:taxonomy:<name>` on term edits and `emdash:settings` on settings; it keeps 404s, preview and editor responses out.
- It is not safe yet. Nothing purges after a site transfer import or `emdash seed` (`transfer/` and `seed/apply.ts` have no route-cache purge), and pages tagged with a collection go stale until `maxAge` after any write EmDash does not purge. A cached book page would also freeze its "Published <today>" line. Tag purge on the Workers cache needs a deploy to test.
- EmDash's object cache (`kvCache()` in `@emdash-cms/cloudflare`, off by default) caches `getEmDashCollection` results in KV with per-namespace invalidation. The link reads in `references.ts` bypass it.

Known limits of the site translator (stated in the guide):

- It covers what the books starter uses. Everything else lands in `tsg2astro-report.md` as not translated.
- Each D1 query is a round trip of about 16 to 37 ms on the test deploy (the Worker answering from IAD, D1 in ENAM; visitors farther from the database pay more). Since the narrow content reads, a shape-books page that queries makes 6 to 14 queries and spends 23 to 96 ms on them (5 to 12 and 87 to 193 ms with the batched reads and coalescing alone); the first deploy made 21 to 64 and spent 0.6 to 1.7 s. Item and listing pages read the columns of the route's whole list that its order and paths need, and only their own entries in full, so rows still grow with list sizes, a few hundred bytes each. Follow-up work: caching, placement.
- A reference to an unpublished entry renders empty: EmDash's public reads skip drafts, where TakeShape returned them. Ruled to stay (Mark, 2026-10-17): the content report lists each draft a published entry links to ("Drafts that published entries link to"), for the owner to publish the ones that should be public. On a large customer site, such drafts account for about half of the compare's remaining differences.
- The image endpoint ignores imgix's effects (`blur`, `sat`, `mark`, `txt` and the rest), `fit=facearea` and `fit=clamp` (resized as clip), `fill=blur` (solid padding), `fp-z`, and `w` or `h` below 1. The report's Image parameters section names each place that passes one. Images without `w` or `h` go out as stored, where TakeShape's CDN compressed them. On Workers, a padded image's transparent pixels take the padding color: the Images binding has one `background` for both (`cloudflareSteps` passes `padColor` there). sharp keeps them apart, `bg` inside and `fill-color` around, as imgix does (unit-tested with a PNG that has a transparent hole; fixed after a code review, 2026-10-16). A two-step binding chain could match imgix on Workers too; not tried, since `wrangler dev` runs the binding offline without most options.
- On Workers, stored images over 20 MB go through `fetch()` with `cf.image` (see "Generated projects"), up to Cloudflare's 100 MB, 100 megapixels and 12,000 pixels a side. Past those the endpoint sends the stored file at full size; Node's sharp resizes them. Through that path an animation keeps its first frame (as on Node; the binding's handling of animations was never checked), a PNG plan can come out as a palette PNG, and each new result has Cloudflare fetch the whole file through the site's media route (up to 3.3 s on a large customer site's test deploy the first time).
- EmDash serves PDF and SVG media as downloads (`Content-Disposition: attachment`, read from source), so links that opened them in the browser now download.
- imgix rendered PDFs (first page) and PSDs as images; the site serves the stored file, which `<img>` can't show. The compare marks such a `src` `[file]` against the old `[image]`.
- An entry edited in EmDash keeps its `takeshape_updated_at`, so `_updatedAt` (a sitemap's `lastmod`) keeps TakeShape's date until someone clears or changes that field. Ruled to stay; the guide and the scaffold's `AGENTS.md` give the workaround.
- Saving rich text in EmDash's editor can change two printed things (see the round trip in the EmDash facts).
- Browser code that calls TakeShape's API is the customer's (or their agent's) job, with the resolve skill. On a large customer site, that meant moving the calls of about ten components to JSON endpoints written from the planner.
- rehost writes site paths (`/_takeshape-files/...`), so a feed's `<image><url>` or a JSON-LD logo it moved is relative; the guide says to put the site's URL in front by hand. Content images and files are absolute.
- Browser code that builds image URLs from the `path` in a data file (takeshape-routing's `getImageUrl`) breaks at once, since `path` is now an EmDash storage key. A `getImageUrl` of the site's own on `/_emdash/api/media/file` fixes it, and the middleware sends media URLs with imgix parameters to the image endpoint (a large customer site's pages checked in a browser, 2026-10-19). Passing `baseUrl` to takeshape-routing's fixes the images as well, but leaves its default `https://images.takeshape.io` in the bundle, which the compare flags. The resolve skill's takeshape-host section says so.
